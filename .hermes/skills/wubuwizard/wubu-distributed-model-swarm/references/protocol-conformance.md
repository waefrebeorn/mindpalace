# Protocol conformance notes

Numbers verified against the published specifications. Write these into an
enum or a golden vector BEFORE the first test run -- a self-consistent encoder
happily emits a self-consistent WRONG wire format, and a golden vector
generated by the code under test proves only that the two agree.

## yamux (libp2p spec)

| type | value |
|---|---|
| Data | 0x0 |
| Window Update | 0x1 |
| Ping | 0x2 |
| Go Away | 0x3 |

Flags: SYN `0x1`, ACK `0x2`, FIN `0x4`, RST `0x8`.

Header is 12 bytes, all multi-byte fields big-endian:
`version(1) type(1) flags(2) streamID(4) length(4)`.

`length` means payload bytes for DATA, a window delta for WINDOW_UPDATE, an
opaque echoed value for PING, an error code for GOAWAY. Stream IDs: odd =
client-initiated, even = server.

## Unsigned varints (multiformats)

LEB128-style: 7 bits per byte, MSB = continuation.

- **Maximum NINE bytes (63 bits).** Implementations MUST enforce this.
- **Must be minimally encoded.** Leading zero groups are invalid on decode;
  `{0x81, 0x00}` means 1 and must be refused. Zero itself is the only value
  allowed to end in `0x00`.

Values >= 2^63 cannot be represented -- refuse them rather than silently
growing to ten bytes.

## protobuf varints

Same LEB128 shape, one deliberate difference: a negative int32/int64 is
SIGN-EXTENDED to 64 bits before encoding, so `-1` is TEN bytes (`ff` x9, `01`).
The multiformats nine-byte limit does NOT apply. Applying the strict profile
here refuses values a peer expects to receive.

Canonical field numbers (go-bitswap schema):

```
Message        wantlist=1   block=2 (deprecated raw bytes)   blockPresences=3
Wantlist       entries=1    full=2
Entry          block=1   priority=2   cancel=3   wantType=4   sendDontHave=5
Block          prefix=1  data=2
BlockPresence  cid=1      type=2
```

Wire types: VARINT 0, 64BIT 1, BYTES 2, 32BIT 5. bitswap uses only 0 and 2 --
refuse the others rather than half-reading them.

## multistream-select 1.0

- Protocol id `/multistream/1.0.0\n` -- **19 bytes**, not 20 or 22.
- Messages are UTF-8 strings ALWAYS terminated by `\n`; the frame length counts
  that newline.
- Both peers send the protocol id first. The initiator then proposes; the
  responder ECHOES the id to agree or answers `na\n`.
- Anything printable ending in `\n` is a string message; anything else is an
  opaque data frame. Do not force negotiated binary traffic through the string
  branch.

## CIDs

v0 = base58btc of `0x12 0x20 <sha2-256>` (46 chars); implies dag-pb +
sha2-256 + 32 bytes and has NO other legal form -- one that is not that shape
must not build at all. v1 = `<version><codec><multihash>` with varints,
multibase-prefixed (`b` base32 lower, `z` base58btc, `f` base16).
Multihash = `<hash-code><digest-len><digest>`.
